# wangbin-tender-analyzer · 输入输出和判定契约（冻结）

权威：Q01 T00 附件19 §19.3–19.7；规则参照 `requirements.md` BID-01–08。以下为新版验收合同，**非**旧 `analyze_tender.py --input` 已实现接口；由开发者选择明确且可测试的新版命令入口和参数，保留旧入口行为不变，并在 SKILL 中记载真实仓库与解压调用路径，不假设 WorkBuddy 具 Python/固定 cwd。所有规则只适用于用户明确提供的有限集合，不作全量投标证明。

## 输入与识别

| 角色 | 必需性/格式 | 验证与解释 |
|---|---|---|
| tender | 所有模式必需；单份 UTF-8 `.txt/.md` | 非空普通非 symlink 文件，≤1 MiB；明确选择且用户自行确认授权；取 basename（防止路径泄漏）。 |
| response | 核查模式必需，准备模式不得伪造；单份 UTF-8 `.txt/.md` | 未提交→准备模式；明确要求核查而未给→`MISSING_RESPONSE`，不自动输出漏答结论。 |
| amendments | 可选、零或多份，UTF-8 `.txt/.md` | 每份保留来源及原句；仅正式补遗、有明确版本/替换关系时参与 supersession；普通说明不得自动当正式补遗。 |
| attachment_catalog | 可选，单份 UTF-8 `.csv` 或合法 `.xlsx` | 仅附件**目录**，不是文件存在证明；CSV 首行或 XLSX 指定表首行为标题，必需列 `附件名称`（非空），可选 `关联要求编号`、`说明`；逐行可追溯 CSV 行号/XLSX 表名+行号。同名多行全部保留并标待确认。拒绝损坏/加密/含无法确定列头的清单。 |
| evidence_files | 可选，零或多份用户显式指定的 UTF-8 `.txt/.md` | 与附件清单名称做受控关联；独立限制同旧文本输入（普通、非 symlink、≤1 MiB），不可仅由目录名称打开路径或递归扫描。名字不对应/存在多个候选→待确认；真实行内容与具体声明相关才可标“支持”（仅文本层面，不认证真伪）。 |
| version_relations | 可选，用户显式指定的关系和来源依据 | 关系双方需是已提交来源/要求，引用补遗具体原句或用户明确的书面版本关系及出处；无出处只作待确认，不当作自动优先级。 |
| project_name / output_dir | 项目名可选，输出目标由用户指定或有文档化的默认值 | 文件名只接受安全单段名称；过滤路径分隔符、`..`、控制字符，阻止越界/覆盖输入；无项目名时使用明确默认名并在输出标注“未提供项目名称”，不猜测。 |

同一文件不应被多个输入角色重复默默读取；文件解码失败、symlink、目录、过大或不支持格式（特别是伪装 PDF/DOCX）明确报错并指出**角色**和稳定错误码，不含原文/私有绝对路径。可选文件若失败可选择整体拒绝（本合同默认）或经用户明确同意局部处理，但局部输出必须写入未核验的来源及影响范围，不能将其视为未要求/已覆盖。XLSX 读取不执行宏、公式或外链，不将公式计算值当证明；公式单元格的关键字段待确认/拒绝。不可未经授权使用外网服务或把敏感原文发给模型。隐私脱敏不是完备识别，报告为人工复核材料。

## 规范化记录与可追溯定位

- `TenderRequirement`: `requirement_id`（唯一、确定性，基于来源角色+文件 basename/来源序号+原文编号或来源行号；basename 冲突时保留来源序号）、`original_number`（可空）、`original_text`（真实原句；在输出时脱敏并标注）、`source`（basename、1 起始行号、摘录及 `redacted excerpt` 标签）、`requirement_type`、`mandatory_quote`（无强制原句则 null）、`explicit_conditions[]`（各条件的来源原句/行号）、`required_materials[]`、`applicable_version`（证据不足则 null）、`amendment_relation`（目标、类型、出处或 null）。重复编号按来源和章节/行区分，不静默合并；不推断文本中未明示的条件或法律后果。
- `ResponseCheck`: `requirement_id`、`response_locations[]`（basename、行号、脱敏摘录）、`response_text`（脱敏来源原句或 null）、`candidate_matches[]`、`attachment_names[]`、`attachment_provided`、`evidence_locations[]`、四维状态与各自依据、`gaps[]`、`conflicts[]`、`pending_questions[]`。没有原文不得构造引文；位置是文本行，不是 PDF 页码。
- 配对：优先编号完全匹配且上下文对上；多文件/章节同号不能凭裸编号选目标。编号改变而内容近似，双方引文+关联理由一并列出，并标人工复核；多候选均列来源，不按首个、最大相似度或关键字自动消除歧义。仅在提供范围内无可对应项才能称“在已提供响应中未找到”，不是断言用户实际没有回应。
- 补遗关系图：保留旧与新记录、边类型（明确替换/撤销/补充/待确认）、双方来源和触发原句。只有有依据的替换/撤销边才令旧要求不再适用；补充边不删旧要求；环/冲突/未知保持并列、需人工确认。不能用文件名、mtime、上传顺序、编号大小决定覆盖。

## 四维状态（每一维各自记录，不许合并）

| 维度 | 合法状态及可复现判据 |
|---|---|
| 响应存在 | `已定位`：响应可定位、关联无歧义；`未找到（限已提供响应）`：核查模式内可检索范围无对应；`候选待确认`：多处或仅语义相似；`未核查`：准备模式/响应无法处理。 |
| 明确条件覆盖 | `已覆盖（文本层面）`：每个明确条件逐项由响应原句支持并有行证据；`可能不充分`：找到响应但至少一项明确条件没有支持；`待确认`：候选歧义或条件本身不明；`未核查`：准备模式/无响应。只说“具备该资质”不等于提供要求的资质证明。 |
| 附件实际提供 | `已提供（可读文本）`：用户确实提供对应可读材料；`仅目录登记`：清单列名但无实际文件；`未提供（限已提供材料）`：要求明确而给定材料集合无关联；`待确认`：关联冲突/文件不可读/未提供完整材料集合。清单缺失不可转为“没有附件”。 |
| 内容支持声明 | `支持（文本层面）`：实际材料存在且相关原句支持具体声明；`不支持（文本层面）`：实际可读材料与声明有明确矛盾/不含明确必需内容，并记录逐条比对；`未核验`：仅目录项、无材料或无法读取；`待确认`：文字含糊、多候选/真伪需确认。不得把文字支持写成证书真伪认证。 |

所有维度允许不适用（要求不需要附件时附件及内容标 `不适用` 并附理由）；不知道与零不同，汇总状态来自行状态而非缺值计数。补附件时仅对其关联的 requirement_id 及聚合输出重算，保留不受影响行稳定；材料存在也不能自动提升内容支持。

## 输出文件及一致性

一次成功写出恰好两文件（输出目标存在时拒绝覆盖或由用户显式授权并安全写入；失败不能留有貌似完整的半成品）。`{项目名称}-投标响应检查.xlsx` 要求五表且顺序固定：

1. `核查概览`：模式、输入文件 basename/范围、每维的各状态计数/未知计数、适用/替换/待确认要求范围、局限与需人工复核项；计数直接从矩阵推导。
2. `要求响应矩阵`：每个 requirement_id 一行（重复原始编号多行），列 `要求编号`、`要求原文`、`来源`、`明确条件`、`响应位置`、`响应内容`、`支持材料`、`证据位置`、`响应存在状态`、`条件覆盖状态`、`附件实际提供状态`、`内容支持状态`、`缺口`、`建议`；补充唯一 ID/版本/候选及理由列确保追溯。
3. `附件核对`：清单条目来源、实际文件来源、关联 requirement_id、是否实际提供、内容支持的具体文本行、未核验理由；目录项与实际材料单独列。目录没有文件不能写“已核验证据”。
4. `补遗与版本`：原要求、新要求、关系类型、来源原句/行、依据、冲突与是否适用；无补遗时显式记无提供，不假造替换。
5. `待确认事项`：关联 requirement_id、问题、触发位置、所需人工动作与影响维度；包括歧义、不可读文件、无法证明的关系与真伪界限。

`{项目名称}-提交前核对清单.md`：模式及范围、确定需要补资料（有证据的缺口）、需要人工确认（不得混同确定缺失）、已覆盖范围/未覆盖范围（仅就给定材料）、对应 requirement_id/证据位置；准备模式标题提示**响应未核查**。两文件相同要求和状态不能互相矛盾；脱敏避免公式注入（任何以 `= + - @` 开头的非可信文本写入 XLSX 必须作为纯文本，不执行）。内容即使内部引用原文也仅可输出真实输入派生的有限脱敏摘录，不能伪造证书/日期或敏感全文。

## 稳定错误与边界

| 错误码 | 触发/结果 |
|---|---|
| `MISSING_TENDER` / `MISSING_RESPONSE` | 必需输入缺；准备模式无响应不是 `MISSING_RESPONSE`。 |
| `INPUT_NOT_FOUND` / `INPUT_NOT_REGULAR` / `INPUT_SYMLINK` | 选择的输入不存在/非普通文件/符号链接；不遍历路径。 |
| `INPUT_TYPE_UNSUPPORTED` / `INPUT_TOO_LARGE` / `INVALID_UTF8` / `INPUT_READ_FAILED` | 格式、文本大小、编码或读取失败；旧单文件入口的既有报错不得改变。 |
| `CATALOG_SCHEMA_INVALID` / `CATALOG_READ_FAILED` | 清单缺 `附件名称`、损坏/加密/无法安全处理。 |
| `RELATION_INVALID` | 显式版本关系指向未提供来源/不合法；仅缺乏替换依据时输出待确认而非伪造关系。 |
| `OUTPUT_PATH_INVALID` / `OUTPUT_EXISTS` / `OUTPUT_WRITE_FAILED` | 非安全路径、既存文件或写出失败，明确告警并清理临时文件。 |

新版 CLI 非零退出时无两个貌似成功的输出；错误不回显私有路径或正文。旧入口仍 `--input`、错误 stderr `ERROR <code>`/exit 2、成功 JSON stdout/exit 0，不能把新 XLSX 入口替换旧接口。开发者应在 SKILL 写出实际确定的参数名、依赖与调用示例，避免规格把不存在的命令当已测事实。

## AUDIT-R1 BID-F01–F05 增量输入、判定、输出合同

本节补强 BID-01–08，不变更以上格式和错误码。只接受上述 `tender`/`response`/可选补遗 `.txt/.md`、目录 `.csv/.xlsx`、实际证明 `.txt/.md`，逐文件需 role+basename+1 起始行或表/行；不得自动扫描目录或从目录名字读取文件。下列记录可作为内部结构或 XLSX/MD 可见等价字段，不强制开发者采用某个类名，但**不允许丢失该信息**：`requirement_id, target_object, target_interval_start/end_or_single_day, target_date_source, target_scope_known, material_duty_kind, duty_source, response_location, response_polarity/scope/condition, evidence_file/line, certificate_object, issue_date, effective_date, expiry_date, each_date_role_source, four_states, per_dimension_reason/gaps/conflicts`。日期一律以来源原句解析为公历日；只有年且范围经明示为全年时才能闭区间 `[YYYY-01-01, YYYY-12-31]`，不能凭证书“签发 YYYY”推定有效起点或期限。日期目标仅单日则比较该日；若需要全年而起止缺/语义模糊，记所缺字段待确认。相同证书对象且双方区间齐备才做闭区间包含判断，边界同日支持；明确 `effective > target_start` 或 `expiry < target_end` 为该日期条件不支持并指出差距，不可用另一证书日期填缺。证书与招标对象无法唯一配对时保持候选，不借时间最大值消歧。

回应与材料检查的决策序：先提取招标义务及其原句→按编号+语境确认响应位置或候选→针对每个明确条件绑定回应的主体、肯否、前提及时间范围→独立判断是否需要附件→区分目录项、用户明示且可读的真实文件、文件正文支持。`必须支持 X`/`不支持 X` 的回应状态为`已定位`而条件为`可能不充分`并保留冲突；`不使用 Y`/`不使用 Y` 在作用域相同时可文本覆盖；`购买模块后才支持 X` 只支持有条件事实，不能作为无条件满足。单纯“将提供/正在申请”不能证明材料已提交。条件不明才`待确认`，不能把可比正反例全部改成`待确认`。对具体材料义务，即使没有扩展名或目录，也要在 `required_materials[]` 记录材料类别和原句并为附件维度赋适用状态；文件名、清单文字及条件提取后空数组都不构成内容支持。实际材料明确反证（如“仅占位，不含证书”）→`不支持（文本层面）`+来源和缺口；正文不含可比较内容→`待确认` 或带理由的 `不支持（文本层面）`（只限明确必需内容已完整检查），不得伪造不具备资质的事实。只提供目录→`仅目录登记`/`未核验`；实际文件关联不确定→`待确认`，不因为 basename 相似而自动认定提供或支持。

每个 `requirement_id` 的四维（响应、条件、附件、内容）分别携带状态、触发来源、明确缺口/不确定原因，写入 `要求响应矩阵`；`附件核对` 中材料义务无目录也须有要求 ID、类别、目录缺失/实际输入范围、内容未核验原因；若无实际材料，证据位置不得指向目录行并宣称材料支持。`核查概览` 四维计数分别由矩阵重算（包括 `待确认/未核查/不适用`，未知绝不计零通过）；`待确认事项` 为不确定原因保留 ID 与来源；MD 已覆盖范围只收**适用维度无确定缺口且相应文本支持**的行，确定需补资料和已覆盖同一义务不得并列，不能以一个维度支持掩盖其他维度缺口。日期反证、否定回应、条件回应和空条件反证须在矩阵缺口、附件核对、概览及 MD 的确定缺口/人工确认分类中同义，不凭任一单元格字符串机械一致宣布业务通过。正式补遗更新及复跑时保持原 `requirement_id`/不受影响行；重新生成两文件且授权输出目标，不就地修改输入。

老合同 `BID-A04` 只有“覆盖2027年”和“有效期至2026-12-31”，**截止端不足可确认**，但若报告声称整段期限有效或某证书对象对应，仍须起点与对象证据；不能写成“见到2026必冲突”。旧 JSON CLI 保留原 `--input` 成功 JSON/错误语义及原 expected 文件，运行指引不得把“actual 写回 expected”作为测试；以独立需求预期和原快照作对照。新增案例未满足时如实报业务 FAIL（即使 CLI exit0），错误输入按上表稳定代码非零、不得留下貌似成功的 XLSX/MD。
