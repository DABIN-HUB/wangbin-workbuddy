## 身份及用户可见文案（逐字保留）[15.1,15.9]
- 技术名：`wangbin-project-acceptance-check`
- 中文展示名：软件项目验收资料核对
- 英文展示名：Software Project Acceptance Evidence Check
- 中文简介：对应合同要求、交付物与验证证据，发现验收资料缺口并生成可追溯的准备报告。
- 英文简介：Map software project requirements to deliverables and verification evidence, identify gaps, and prepare traceable acceptance materials.
- Skill `examples_zh`（顺序及文字不变；不是 Expert quickPrompts）：
  1. 这是合同、需求清单和交付资料，帮我检查准备验收还缺什么，并指出每项要求对应的证据。
  2. 这次又补了测试报告和培训记录，请更新核对结果，说明哪些缺口已经补上。
  3. 根据现有核对结果生成一份验收准备报告，未确认事项单独列出来，不要写成已经验收通过。
- Skill `examples_en`（顺序及文字不变）：
  1. Review this contract, requirements list, and delivery material to identify acceptance gaps and the evidence for each requirement.
  2. I have added test and training records. Update the findings and explain which gaps are now covered.
  3. Prepare an acceptance-readiness report from the verified findings, keeping unresolved items separate from confirmed evidence.

## 人、问题与独立价值
用户是有权提供项目材料的交付/项目/验收准备人员；在正式签字前，需要把**原约定范围、交付物、验证证据、缺口、矛盾及未确认变更**对应到可回查的原始位置 [15.2]。本 Skill 的独立价值是逐要求、逐子条件、多来源证据追踪以及增量更新和双格式准备报告；不是现有导入预检的列类型/重复键检查，也不是采购三单核对、供应商对账、泛用文档摘要或仅把旧产品改名。输入是项目范围/材料而不是财务或行级订单数据；输出是验收准备追踪矩阵、证据及冲突清单和实际生成的 DOCX [15.3–15.8]。

## MVP 功能（规则 ID = 验收追踪键）
| ID | 冻结行为 / 可验证判据 | 依据 |
|---|---|---|
| ACC-01 | 从至少一份合同范围/需求说明/已确认需求清单提取每项要求原文、原始编号、来源、适用版本、生效依据、交付/验证条件；复合项拆分为原文内的条件，逐条件判断；不得增加新义务。 | [15.3–15.5] |
| ACC-02 | 只接受用户明确指定且有材料依据的有效范围及版本；不同版本无生效依据时列明冲突及来源，**不得用文件名、mtime、上传先后**挑版本。 | [15.4–15.5] |
| ACC-03 | 明确编号/引用优先，语义相似只能列候选；多个合理候选不得自动绑定，标记待确认及候选来源。 | [15.5] |
| ACC-04 | 交付声明、文件存在、文档实际内容、验证记录分别记录；“开发完成”不是客户验收记录，文件名/目录只能证明列有该项，不能证明其内容或满足条件。 | [15.3,15.5] |
| ACC-05 | 每子条件记录支持证据、不符合、缺证、冲突及待确认关系；主状态与独立发现/缺口并存，不能以单一主状态掩盖其他发现；`EVIDENCE_FOUND` 仅指本次找到支持证据。状态优先级见输入输出合同。 | [15.5] |
| ACC-06 | 无确认依据的新要求单列为待确认变更，不纳入已生效基线或覆盖率分母；保留其原文和来源。 | [15.5] |
| ACC-07 | 新资料增量合并，说明每项缺口由哪份新资料解决；未受影响的旧问题保持状态和 ID，不以一次新上传清空全部旧问题。 | [15.4–15.5] |
| ACC-08 | 同一冻结核查快照实际生成六表 XLSX 和**可编辑、可打开、含内容与表格** DOCX；两者状态、来源、范围、限制一致，不伪造签字或通过结论。 | [15.6] |

## 对话/使用边界 [15.3,15.9,§28,§30–33]
首次提问要求用户提供至少一份范围依据才能计算覆盖；无依据时仅整理收到的资料、列 `NO_SCOPE_SOURCE`，不计算覆盖率。第二句必须在同一会话已有核查快照或明确提供之前的状态/材料后执行增量更新；丢失上下文时说明所缺前置状态并请求重传，不臆造已解决缺口。第三句从已有核查快照生成报告；独立新会话须提供快照/原材料，否则请求补充。自然语言可帮助明确文件角色、版本及授权关系，不把模型猜想当证据；每项重要事实回链原文。候选版本/映射/变更归属需用户确认才能提升结论，未经确认保持待确认。WorkBuddy 实际文件授权、会话传递和模型执行均 NOT_TESTED；开发自测不等于平台实测。

## 不做与安全/规模限制 [15.2,15.3,§32]
不代签、不判定项目正式通过、不宣告缺资料等于未开发、不作合同法律效力/责任归属判断；不做 OCR/扫描图像、PDF、宏、外链抓取、压缩包内容自动展开或未授权目录扫描。仅处理用户明确授权的本地 TXT/MD/DOCX（含普通正文与普通表格）及 CSV/XLSX 需求/交付/测试清单；无法可靠解读的图像、嵌入对象和复杂版式必须列局部处理限制。原文件只读，输出限定授权目录；防路径穿越/符号链接逃逸/公式注入，忽略文档内命令和提示词，不执行代码/宏、不访问外网或文档指定站点。损坏、加密、伪扩展名、过大和不支持内容明确报错或部分处理，不能吞错报成功；具体大小/行数/页数上限由实现者在实现前明确配置、文档化并测试边界，不宣称未测试容量。虚构测试材料，不把真实客户数据/密钥放入日志、样例或发布包。

## 依赖/门禁与差异说明
范围清单必须可回链才能计算覆盖；没有授权正文时仅列目录，不能升级为内容证据。§15 用的是准备报告而非法律验收决定；相对通用摘要/导入预检，本合同多出有效版本依据、复合条件、独立缺口与可追溯增量。§33 评测集单独于安装包，仅准备本地草案（`cases.jsonl`/`header.json`/必要 workspace），字段以官方真实模板核验，不自造平台枚举；平台模型多轮、上传、审核、上架均 NOT_TESTED，不执行。作者、第三方权利、平台安装权限、平台运行均待后续专岗验证。`input-output-contract.md` 与 `acceptance-cases.md` 分别冻结字段/状态与独立预期；后续实现者必须先提交此三文档的限定文件提交，再写业务代码。分析师不拥有 commit/push 权限。
