# Q02 输入输出及确定性判定合同（V2 冻结）

依据: t_a9f8fe9d attachment19 §15 行 720–945、§32–33 行 2444–2499；`[D]` 为实现前明确的可测试细化，不是原文直接规定。样例均为虚构项目“星桥演示平台”。

## WorkBuddy/本地执行参数边界 [15.3,15.9,D]
调用者明确提供 `project_name`（非空、文件名安全）、`authorized_input_root`、`output_dir`（受授权、不可越界）、`scope_sources`（合同范围/需求说明/已确认需求清单，可空但必须降级）、`delivery_sources`/`evidence_sources`/`change_sources`（可空）、`effective_version_ref`（可空，用户指定的来源定位和范围/版本，须能回查）、`previous_snapshot`（增量时可空，非增量无须）。文件从用户授权附件或显式受限路径取得；自然语言仅映射这些参数，无法确定附件角色时请求确认，不自行扫描其他文件、访问外网或把对话意图当确认文件。实现须提供可复现实跑的本地入口及 `--help`；**CLI 参数名和命令尚非已实现 API**，T02 落地时以实际 `--help`/测试命令回填，不虚构存在的接口。缺 `project_name`/非法输出目录拒绝；无范围依据允许整理现有材料但输出覆盖率 `N/A`、`NO_SCOPE_SOURCE`，不得报 0%。

## 支持文件、必需字段与校验 [15.3–15.4,D]
- TXT/MD：UTF-8（允许 BOM），按自然段/标题/列表记录物理行号；非 UTF-8 可明确报编码错误，不默默替换坏字节。DOCX：真实 OOXML 正文段落与普通表格；表格定位为 `表格序号/行/列`，合并单元格不得复制成多条原始要求；无法读取的图片/嵌入物标 `UNSUPPORTED_CONTENT`。
- CSV：UTF-8 BOM 可接受，标题行字段名映射须显式；XLSX：指定工作表或可明确识别的清单表，保存 `工作表/行/列`；公式不执行，不将无缓存公式结果当事实。扩展名与文件签名/解析双重检查；损坏/加密/宏格式/伪扩展名、空文件显式报错。列表只支持需求、交付、测试记录，不默默把任意表解释为合同。
- 范围来源至少一份为覆盖判定前提，要求最小字段为**要求原文（非空）**及其源文件与定位；原始编号可缺失但标 `MISSING_ORIGINAL_ID` 并生成内部 ID，不臆造编号；适用版本、交付条件、验证条件、子条件、生效依据缺失时记 `NOT_SPECIFIED`，不能自动视为满足/零项。若没有可解析要求，则无覆盖率。重复原始编号不覆盖：按来源命名空间保留独立记录，展示重复冲突待确认。
- 交付清单最小字段为**名称（非空）**、源位置；类型/版本/相关声明和实际内容可空但必须区分 `NOT_PROVIDED` 与 `PRESENT`。目录项只有名称时 `LISTED_ONLY`，不能充当内容或测试证据。测试清单/证据最小字段为**证据原文或可读取记录内容（非空）**、源位置；编号/引用、证明范围、确认状态不明时标未知，不能推定客户确认。变更材料需变更原文、来源和明确确认依据才可更新有效范围；否则另列待确认。[D]
- 所有来源 `source_id` 是授权导入时分配且在快照中保留的稳定标识；记录源文件相对授权根目录路径、文件内容 SHA-256、文件类型和真实定位。`requirement_id`/`deliverable_id`/`evidence_id` 为**工具生成**，命名空间含 source_id + 来源结构位置 + 原始记录序号（重复编号不复用），在已保存快照增量导入时复用既有 ID；新增源只追加新 ID，重名/路径冲突不得覆盖。文件被重排或改写、来源标识不可信时展示旧新定位并标 `IDENTITY_REVIEW`，不得以哈希变化悄悄重写全部旧 ID。[15.4,D]

## 对应、状态和覆盖率 [15.5,D]
1. 先按明确要求编号/原文引用定位候选；重复编号需加来源命名空间/确认关系。没有明确唯一引用时，语义相似只产生候选；两候选或关系不确定则 `PENDING_CONFIRMATION` 并列候选位置，未获确认不得绑定。[ACC-03]
2. 每子条件记录 `condition_id`、原文片段、支持/不符合/缺失/冲突/待确认发现、证据 ID 和来源位置；没有条件文本不能编造义务。核查矩阵每要求至少一行；同一要求若证据明确不符合且另有缺资料，独立发现两条都保留。[ACC-01,04,05]
3. 主状态只取这六个枚举，**从高到低**：存在影响该要求的未解决证据冲突 → `CONFLICT`；明确不符合 → `NONCONFORMING`；影响结论的关系或有效版本待确认 → `PENDING_CONFIRMATION`；有些子条件获可靠支持但仍有未覆盖 → `PARTIAL_EVIDENCE`；全部适用子条件均找到可靠支持且无更高优先事项 → `EVIDENCE_FOUND`；否则 → `NO_EVIDENCE_FOUND`。即使 `CONFLICT`，仍保留独立不符合与缺失。待确认新增要求放变更栏，不在既有范围矩阵假装已生效。`EVIDENCE_FOUND` ≠ 通过正式验收。[ACC-05,06]
4. 覆盖率只对**有权威生效依据且可枚举条件的有效范围**计算；无范围/版本冲突影响分母时输出 `N/A` 并解释，不报告 0 或虚假确定率。若需要数值，展示已支持子条件数、适用条件总数及计算口径；无可判条件则 `N/A`。不把目录项/声明/未确认候选记为已支持。[D]
5. 增量更新使用上一核查快照与新授权文件；保留历史发现和源定位，逐项列 `RESOLVED`/`UNCHANGED`/`NEW`/`REVIEW_REQUIRED` 以及解决该缺口的新增证据 ID；不同结论的新旧证据并列显示，不能仅因上传时间较晚覆盖旧证据或自动修改有效版本。[ACC-02,07]

## 输出及必需结构 [15.6,D]
成功且有可处理材料时，同一批核查快照输出到受限目录：`{项目名称}-验收资料核对.xlsx` 和 `{项目名称}-验收准备报告.docx`，另保存可供增量使用的结构化快照（文件名及模式由 T02 实现并记文档，不能由 XLSX 展示值反推丢失的证据关系）。项目名称清理非法文件名字符须显式通知、不覆盖已有文件而无确认；输出应原子写入，部分失败不得报成功。XLSX **恰含指定六工作表且顺序如下**：
1. `核查概览`：项目、核查范围、有效版本/依据、材料/限制、覆盖率或 N/A、各状态数量；
2. `要求追踪`：`requirement_id`、`原始编号`、`要求原文`、`来源`、`验收条件`、`对应交付物`、`证据位置`、`核查结论`、`已覆盖子条件`、`未覆盖子条件`、`缺口`、`下一步确认事项`；
3. `证据索引`：evidence_id、来源位置、原文、证明范围、关联 requirement_id/condition_id、确认状态；
4. `缺口与不符合`：独立发现 ID、要求/子条件、类型、原文及来源、是否解决、下一步；
5. `冲突与待确认`：各版本/测试冲突候选及来源、待确认关联、未确认新增范围、所需确认；
6. `本次更新`：旧/新发现 ID、变更类型、解决证据来源、未受影响项状态。
所有引入单元格的用户文字以**文字**写入并阻止 `= + - @` 等公式触发，不执行公式/外链。可编辑 DOCX **实际生成并能用 docx 解析重新打开**，标题与正文写“验收准备／草稿”，章节顺序为 `项目及核查范围`、`本次资料与有效版本`、`主要发现`、`要求与证据概况`、`资料缺口和明确不符合`、`冲突及未确认变更`、`验收准备建议`、`来源和限制`；至少含逐要求状态/证据表以及缺口表，引用与 XLSX 同一快照 ID、来源位置和主状态，不含伪造签字/验收通过结论。[ACC-08]

## 错误与局部处理状态 [15.3,§32,D]
`INVALID_INPUT`（无效/不安全参数）、`UNSUPPORTED_FORMAT`（不支持或伪扩展名）、`UNREADABLE_SOURCE`（损坏、加密、坏编码、空文档）、`UNSUPPORTED_CONTENT`（只支持正文/普通表格，记录不可处理部分）、`RESOURCE_LIMIT`（超实现公布上限）、`NO_SCOPE_SOURCE`（可继续整理但不可算覆盖）、`VERSION_CONFLICT`（可继续列冲突但覆盖 N/A）、`OUTPUT_FAILED`（任一输出失败不能报完全成功）、`IDENTITY_REVIEW`（无法安全匹配旧 ID）。错误逐文件标路径、位置/原因和已处理范围；有有效部分可输出 `PARTIAL` 且列表指出未覆盖部分，不能以空成功代替失败；全无可处理内容返回失败且不生成误导性完整报告。进程退出码本冻结建议 `0` 完整、`2` 输入/格式失败、`3` 部分可处理、`4` 输出失败；T02 若入口遵循其他既有规范须显式记录映射并让验收断言实际帮助，**这些数字不是已验证的平台退出码**。源文不修改，诊断不泄露未授权路径/客户正文。

## AUDIT-R1 ACC-F01–F04 事实与判定补充合同（t_4ddc9074）
此处补充上方 §15 合同，不把原 `ACC-03` 的“编号优先”读成编号即支持，也不把 §15.7 的 Windows Server 2019 样例读成枚举白名单。新一轮具体规则由附件19 §15.2–15.8、审查 §07 驱动；旧包探针 `docs/qa/audit-r1-012-baseline-results.json` 仅提供旧实际，不提供正确预期。新版本尚未测试。

**可执行事实链：**从用户授权的 TXT/MD/DOCX 普通正文/表格、CSV/XLSX 清单中，逐项记 `source_id`、相对路径+行/表格单元格、原文、`requirement_id/condition_id/evidence_id`、显式编号/引用及关系依据；标注证据性质（目录 `LISTED_ONLY`、自述 `CLAIM_ONLY`、实际可读内容/测试记录、是否有客户确认）。数值条件提取 `object, metric, comparator, threshold, quantity_unit, scenario, scope`，结果提取 `object, metric, actual_value, quantity_unit, scenario, scope, polarity`；环境条件提取 `target_os, target_version, required_steps`，证据记录实际 OS/版本和已有步骤；测试条件记录 `test_object, test_scope, executed, passed, failed, negation`。字段取不到记 `UNKNOWN` 与具体缺项/来源，不把 NULL 写 0。解析/模型生成的结构事实须由原文支持并经类型、来源及数值校验，模型猜测不得进支持/不符合结论。

1. 编号只筛候选，之后对每个子条件比较对象、度量、场景、单位和数值。`至少 N` 为 `actual >= N`（含等号），`高于 N` 为 `actual > N`，`不超过 N` 为 `actual <= N`；其它比较词必须能映射到明确运算符，歧义待确认。不以字符串包含数字判断；10000 个**并发登录人数**与 12000 次/日登录不能直接换算；同量纲同口径且有明确换算依据才能换算，缺单位/数量/场景则记录不可比，不宣称满足或明确不符合。可比不足才 `NONCONFORMING`；可比达到才 `EVIDENCE_FOUND`；无关备份证据只留关联候选及无关说明，不能计已覆盖。若语句有其他独立条件，需逐项判断后汇总，不能凭单个数完成整个要求。
2. 部署文档核的是本次提供内容是否覆盖目标系统/版本和要求的步骤。Ubuntu-only 对 Windows Server 2022 或 Debian 12 目标，仅其他环境存在时标目标证据未找到（`NO_EVIDENCE_FOUND`；若关联/版本不确定则 `PENDING_CONFIRMATION`）且说明不能推断软件不支持；**明确**“仅 Ubuntu、未提供 Windows Server 2022 步骤”的已关联文档构成所交文档的 `NONCONFORMING` 发现。对应目标系统+版本且所需完整安装/配置/启动/验证步骤有来源则 `EVIDENCE_FOUND`；缺步骤按子条件 `PARTIAL_EVIDENCE`/`NO_EVIDENCE_FOUND`，明确声明缺该步骤才记录不符合。替换 OS/版本不改变规则。
3. 全部测试通过需明确测试对象、范围和执行事实；在确定相同范围 `executed=100, passed=100, failed=0` 支持，无论原文含“失败”二字；`executed=100, passed=99, failed=1` 是可比范围的不符合。互相矛盾的计数或同号多来源相反结论按 `CONFLICT` 并保留双方及独立发现，不能择较晚者；仅“未发现失败”无范围或未给执行总数为覆盖待确认 `PENDING_CONFIRMATION`，**非**确证失败或全量支持。对于 0 与空值/未提及明确区别，不能假设通过数等于总数。
4. 复合交付项先拆出**原文已有**各子条件，接口文档可读且对应要求、部署说明缺失时 `PARTIAL_EVIDENCE`，两项确证文本支持才 `EVIDENCE_FOUND`；只有“开发完成”不作交付/测试支持。新材料须使用 `previous_snapshot` 引用的受控旧事实+新来源比较，保留未受影响 ID、状态和发现；若旧证据被新证据反驳，保持冲突并显示新旧双方。没有快照不得捏造 RESOLVED。不可比较项保留其候选关联/未知原因，不得统一判 `PENDING` 以隐藏可确定的正反例。

**输出、错误与核验：**沿用原六表、同名 DOCX 与增量快照，逐条件存实测值/阈值/单位/场景/版本/失败数或缺失原因、运算及对应来源，主状态遵循上文 §16 优先级；独立缺口/不符合/冲突不得被主状态覆盖。覆盖分子仅计有依据支持的有效子条件，未知值不算零；同一快照在 XLSX、DOCX、JSON 的要求/条件数、状态、证据 ID/行号与未覆盖数量应一致。`INVALID_INPUT`、`NO_SCOPE_SOURCE`、`UNREADABLE_SOURCE`、`UNSUPPORTED_CONTENT`、`OUTPUT_FAILED` 等原错误合同沿用，部分可读必须标覆盖缺口，不能空成功；明确不符合是**业务结论**，CLI 进程可正常退出，不能只凭 exit=0 判断业务 PASS。严格输入授权和防公式注入；日志不泄露客户正文。供后续角色记录实际 `--help`、依赖/版本、最终 ZIP SHA 和命令退出码；无宿主/平台实测则 L4/L5=NOT_TESTED。
