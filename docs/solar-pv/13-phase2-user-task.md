## 三、Phase 2 核心开发目标

### 目标 A：实现完整的数据模型

目前基线记录了 469 项输入字段，包括标量、对象数组及前置任务 ID 数组。

要求建立真正可运行的数据结构及 Schema，并覆盖全部现有字段。

每个字段必须保留：

1. 唯一字段 ID。
2. 中文名称。
3. 英文名称或技术标识。
4. 数据类型。
5. 单位。
6. 合法值范围。
7. 是否必填及条件必填规则。
8. 适用光伏项目类型。
9. 适用计算和报告章节。
10. 数据取得方式。
11. 缺失时允许采取的处理方式。
12. 来源及证据要求。
13. 验证状态。
14. 与公式变量的绑定关系。
15. 版本或基线引用。

不允许为了简化开发而删减字段。

对于未来才使用的字段，可以保留为可验证、可序列化、可追溯的定义，但要如实记录其业务计算尚未实现。

### 目标 B：建立数据来源与可信度体系

每一项关键数据都要支持来源追踪。

至少支持：

- USER_PROVIDED：用户提供。
- DOCUMENT_EXTRACTED：从附件提取。
- EXTERNAL_SOURCE：从外部可信来源获取。
- CALCULATED：由确定性公式计算。
- ASSUMPTION：明确标记的测算假设。
- UNKNOWN：未知或没有充分资料。

不得将模型推断的信息默认为已核实数据。

建议建立统一数据信封，保存原始值、规范化值、原始单位、目标单位、数据来源、采集时间、适用时间、验证状态、可信度以及证据定位。

对于附件来源，应能定位到实际文件及可核实的页码、表格、单元格或文本片段；如果解析器不能可靠提供精确位置，必须返回未能确定的位置状态，不能编造页码。

用户输入与外部来源发生冲突时，不得静默覆盖，必须记录冲突并提供待确认项。

### 目标 C：实现单位归一化与数据校验

需要支持光伏及财务领域涉及的单位转换，包括但不限于：

- W、kW、MW、GW。
- Wp、kWp、MWp。
- Wh、kWh、MWh、GWh。
- 元、万元。
- 元/Wp、万元/MWp。
- m²、公顷、亩。
- kWh/m²。
- 元/kWh。
- 百分数与比例值。
- 日期、时刻、持续时间。
- 经度、纬度。
- 摄氏度及其他适用气象单位。

注意：

**物理量、金额、比例、时间与直流/交流容量的含义不能因为数值可转换就直接混用。**

例如：

- 1MWp 是直流装机容量，不得自动认定等于 1MWac。
- 1,000kWh 是电能，不是瞬时功率。
- 0.8 与 80% 可以在明确单位口径下转换。
- 100 万元和 100 元不能混淆。
- 含税和未税成本不能直接相加。
- 不同年度价格不应在没有价格基准处理的情况下直接比较。

为每一类转换建立正确、异常、边界及反向转换测试。

禁止静默截断精度和自动猜测不明确的单位。

### 目标 D：实现项目分类隔离

严格按 `07-category-boundaries.md` 中冻结的九类光伏项目进行类型定义，不得根据本提示词自行重新划分或删减分类。

建立共同数据模型与独立项目分类扩展。

共用层可以包含：

- 项目身份。
- 地理坐标。
- 太阳能资源。
- 建设时间。
- 设备基础信息。
- 投资目标。
- 来源追踪。

不同类别必须具备专属数据契约。

**工商业屋顶项目**至少独立处理：

- 屋顶面积及可用面积。
- 屋顶朝向和坡度。
- 屋顶结构与荷载资料。
- 屋顶产权及租赁条件。
- 用电负荷。
- 电价。
- 自发自用及余电上网模式。
- 接入点和变压器条件。
- 建筑使用年限。

**地面集中式项目**至少独立处理：

- 土地面积。
- 土地性质和权属。
- 地形地貌。
- 基础及地质条件。
- 送出线路。
- 升压站。
- 电网接入及电量消纳。
- 工程施工条件。

其他七类必须保留各自独立扩展边界，但本阶段不要求实现其全部计算模型。

不得把工商业屋顶的负荷、自用率或屋顶租赁模型直接用于集中式地面项目。

### 目标 E：实现资料完整度分级

根据冻结规范实现 L1、L2、L3 资料等级。

L1：初步筛选资料。

L2：具备完成预可研评价所需的关键资料或明确适用的测算假设。

L3：具备更充分的工程、商业、财务及合规资料。

具体准入条件必须从基线中读取和实现，不得擅自降低标准。

必须支持条件必填。

例如：

- 工商业项目采用自发自用模式，应检查负荷与电价数据是否满足相应测算条件。
- 无贷款项目，不应强制填写贷款利率和偿债计划。
- 有贷款项目，必须检查融资参数及其一致性。
- 未确定装机容量时，可以允许通过后续面积和方案计算估算，但本阶段不应编造估算结果。
- 缺少正式并网意见时，不得把接入条件标记为已经确认。

每个项目完整度结果必须包含：

- 当前等级。
- 已具备资料。
- 缺失的必需资料。
- 存在冲突的资料。
- 尚未验证的假设。
- 能否进入下一计算阶段。
- 下一步需要用户补充的信息。

避免简单采用“已填写字段数量百分比”判断项目能否达到 L2 或 L3。

### 目标 F：实现分阶段智能资料收集

系统不能一次向用户展示全部 469 项字段。

请实现与 WorkBuddy 交互层解耦的数据收集状态机或等效机制。

流程：

1. 用户输入项目位置和项目类型。
2. 系统识别项目分类。
3. 收集最小输入集。
4. 分析关键缺失字段。
5. 按影响优先级生成下一轮问题。
6. 用户继续补充。
7. 对新数据进行校验、归一化和来源登记。
8. 更新资料完整度等级。
9. 输出规范化项目资料。
10. 用户能够修改已有数据并重新进行完整度判断。

用户填写的目标投资回收期只能作为投资约束，不得被当成实际项目财务测算结果。

要求至少实现可通过 JSON 或 CLI 驱动的本地多轮流程，以便在正式 WorkBuddy Expert 接入之前完成自动化测试。

### 目标 G：实现安全的附件解析

优先评估并复用当前 `document-engine` 和 `financial_xlsx.py`。

本阶段支持通过已有实际能力读取：

- DOCX。
- PDF。
- XLSX。
- CSV。
- TXT。
- Markdown。

对于 CSV 等未由现有引擎统一处理的格式，应增加专门的受限解析流程。

附件解析主要识别：

- 项目基本信息。
- 地理位置。
- 屋顶或土地面积。
- 装机计划。
- 电费账单。
- 企业负荷。
- 设备报价。
- 工程造价。
- 并网信息。
- 融资资料。

对于复杂表格、图片、扫描件或 OCR 缺失的内容，不得把解析失败当成数据不存在。

如果没有可靠证据，不得自动声称已成功识别原文件中的参数。

严禁执行用户文档中的宏、脚本、公式或嵌入代码。

继续遵守原有文档引擎的安全限制；已知的 Windows 进程隔离和资源限制问题不能因本阶段复用而被宣称解决。

### 目标 H：建立公式变量与输入字段映射

Phase 1 已冻结 89 条公式和相关字段绑定。

Phase 2 不要求执行全部公式，但必须建立完整可检查的绑定关系。

每个公式应当可以查询：

- 公式 ID。
- 公式名称。
- 中文解释。
- 每个变量的定义。
- 每个变量的单位。
- 每个下标的含义。
- 输入字段 ID。
- 数据类型。
- 数据来源要求。
- 必需参数。
- 条件必需参数。
- 计算状态。
- 适用场景。
- 适用限制。

如果某公式缺少输入，应能够准确识别缺少哪些变量和数据，而不是直接返回 0 或编造默认值。

所有绑定必须引用冻结的字段 ID 和公式 ID，不能创建第二套互不兼容的定义。

特别注意金额血缘、融资条件、合法时间范围及前置任务数组，这四项已经在 Phase 1 审阅中修正，必须有对应回归测试。
